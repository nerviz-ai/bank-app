## 3 · Consumer adapter and idempotency

No consumer in this project for this event. The KYC verdict that comes back is consumed by
**`BL-03`**, which designs its own listener and dedupe.

**Who absorbs the duplicate**

| Consumer | Where it lives | Idempotency | Evidence |
|---|---|---|---|
| KYC application | **outside this project** — another application | **unknown** | user's answer in `use-case-design` — not confirmed with the KYC team |

Duplicates are expected by design: a send that succeeds followed by a mark that fails resends
the row on the next pass. With dedupe **unknown**, the KYC application may run the
verification twice for one customer and answer twice. **Finding for the final report.** What
this side guarantees: every message carries a stable `eventId` and the `customerId`, so the
receiver can dedupe on either once it chooses to.

## 4 · Retry and DLQ

Form B, producer side. There is no consumer here, so no consumer DLQ topic.

| Failure | Handling — the guarantee the relay owes |
|---|---|
| Send fails (timeout, broker down, not acknowledged) | the row stays pending; attempts counted; **per-row exponential backoff** — the next attempt of a failed row is not before 2^attempts × 1 s after the failure, capped at 5 min — other rows keep flowing |
| 10 attempts exhausted | the row is flagged **dead-lettered** and stops being re-read; never deleted, never retried forever. Counter `outbox.events.dead_lettered` incremented; monitored |
| Pending too long | gauge `outbox.pending.age.seconds` (age of the oldest pending row) exported every pass |
| Producer-level transient error | the Kafka client's own idempotent retries inside `delivery.timeout.ms` — no duplicate from the client itself |

A dead-lettered row means a customer stuck in `KYC_IN_PROGRESS` with no request delivered:
an operational incident, not a log line. Re-driving it is an operator action, out of scope
here (§ 9).
